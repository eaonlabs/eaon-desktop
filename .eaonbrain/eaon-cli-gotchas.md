What cost time building [[Eaon CLI: the desktop's main process in a terminal]] and [[Eaon CLI coding layer: what was taken from opencode and why]].

- **Local models arrive late.** `refreshLocalProviders` runs in the background at boot, so Ollama briefly shows 0 models. One-shot commands (`ask`, `doctor`) must `await localModelsReady()` from `runtime/boot.ts`, or they report "no model". The TUI just redraws on `providers:changed`.
- **The trading engine's first refresh waits 5 s** (`START_DELAY_MS` in `features/trading.ts`). Until then the account is null and the desk would show "NAV —", so the desk calls `trading:refresh` as soon as it opens if there's no account yet.
- **`normalizeSymbol` only accepts stock tickers.** ^VIX, GC=F, EURUSD=X and BTC-USD all throw. The desk's rates, commodities, FX and crypto page uses its own Yahoo chart reader in `cli/src/core/market.ts`, with the same `Mozilla/5.0` UA fallback. Orders still go through the engine and stay stock-only.
- **The desktop's key vault** is `keys.dat`, written by Chromium OSCrypt: a `v10` prefix, AES-128-CBC with an IV of 16 spaces, and a key from PBKDF2-SHA1(password, "saltysalt", 1003 rounds, 16 bytes). The password is the keychain item service "Eaon Safe Storage", account "Eaon Key". When a different binary reads it, macOS shows an allow dialog, so read it asynchronously, never with spawnSync. The CLI's own item ("Eaon CLI Safe Storage") is created with `security -i` fed on stdin, so the password never appears in `ps`.
- **The TUI must swallow console output.** Main modules `console.error` freely, and one line would tear the screen. `tui/start.ts` sends console output to `<profile>/logs/cli.log` while the app is up.
- **An approval only shows in Chat.** A chat agent waiting on an approval while the user is on another tab would wait silently, so `App.draw` puts a yellow "waiting for your approval — F1" banner over every other tab.
- **Drawing must not read the store.** `store.getSettings()` reads and merges the settings file on every call, and the screen draws many times a second. A CPU profile of a 77 s session found 5.6 s spent drawing, 1.5 s of it in `getSettings` and 1.9 s in `chatModel`. Use `viewSettings()` from `core/models.ts` for anything drawn (kept for 250 ms); providers are cached for 1.5 s and the bus peer count for 2 s. Anything that *acts* on settings, like `send()`, reads the store directly.
- **The approval mode is read once per turn** by the agent loop, so a mode change mid-turn needs `allowedNow()` in `core/chat.ts`. See the coding-layer note.
- **Program output carries ANSI escapes.** The canvas shows ESC as a space, so `[41m` appeared in command output. `plainOutput()` in `tui/term.ts` strips CSI/OSC sequences and keeps the last state of `\r` progress lines.
- **Testing a TUI.** `node-pty` (built by `fix-node-pty`) and `@xterm/headless` both load under plain Node. A PTY harness can type keys and rebuild the screen as text. Send keys **before** waiting on a screen condition; the other order waits for something that can't happen yet. Ctrl+C quits only with two presses inside 2 s. The first one closes an open dialog, stops a running reply, or clears a non-empty composer (after `/undo` the prompt is back in it), so a harness that sends two may not quit. An `until` regex must match only the final state. `✗ ` also matches an LSP error line mid-turn, and keys sent then land in a busy turn.
- **Profiling the CLI:** run it with `NODE_OPTIONS="--cpu-prof --cpu-prof-dir=…"`. The profile is written at a clean exit. A long gap with only a handful of samples means the process was descheduled, not busy. On a 24 GB Mac with gpt-oss:20b (12.5 GB) generating, the CLI saw stalls of up to ~0.6 s that were not its own code.
- **HTML snapshots** need non-ASCII glyphs pinned to `width: 1ch`/`2ch`, because Chrome's fallback fonts draw braille wider than a cell and charts spill.
- **Ollama models:** qwen3.5:9b's tool calls made Ollama fail with "XML syntax error … element <function> closed by </parameter>". gpt-oss:20b works, as in [[Agentic trading: protective exits, the agent's market view and live testing]]. At Low effort it makes sloppy one-line edits, for example dropping a `return`. The language-server check catches these, which makes it a good live test of that loop.
- **"Could not reach Ollama" on the first turn, sometimes.** It happened in 2 of 6 TUI runs on Oct 3, 2026, each time on the first chat request after launch, while gpt-oss:20b was not loaded. Sending again worked. The message comes from the desktop's own adapter (`providers/adapters/ollama.ts`), which retries HTTP errors but not a rejected `fetch`. A stale keep-alive socket was ruled out: a GET followed by a POST 1–10 s later never failed. The cause is still unknown. The next step is to log `error.cause` in that `catch`, then probably retry a network failure once.
